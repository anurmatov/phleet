# Agent identity

How a fleet MCP server knows which agent is calling it, and what that agent may do there.

## The problem this solves

An agent reaches the fleet's own MCP servers (the orchestrator, fleet-memory, fleet-telegram, the
Temporal bridge) over the Docker network. Until this, a caller said who it was in the URL
(`?agent=name`) and was believed, the orchestrator's MCP endpoint asked for nothing at all, and
the list of tools an agent is granted was enforced only by the provider's CLI inside the agent's
own container. An agent with a shell could call any tool of any of these servers under any name.

## How it works

- **A key.** `FLEET_AGENT_IDENTITY_KEY` in `.env`, generated by `setup.sh` and added by
  `upgrade.sh` when it is missing. It is its own key: identity does not depend on the journal or on
  any other feature being on.
- **A token per agent.** At provisioning the orchestrator signs the agent's name with the key
  (`fa1.agent.<name>.<mac>`) and writes it into the agent's MCP configuration as an
  `Authorization: Bearer …` header on each of the fleet's own servers the agent reaches. There is
  no token table: the same agent gets the same token under the same key.
- **Servers verify.** A server that has the key takes the caller's name from the token. One agent
  cannot make another's token, so it cannot call as another agent.
- **Grants are checked on the server.** A verified agent may call a tool only when its stored
  tools include it (`mcp__<server>__<tool>`, or a grant of the whole server), and is listed only
  those tools. The stored tools are the authority: a tool taken away is refused at once, before
  the agent is reprovisioned.
- **Services are not agents.** A service token (`fa1.service.<name>.<mac>`) identifies a fleet
  service or the operator. It is not held to any agent's grants.

The URL still carries `?agent=name`. A server from before tokens reads it as it always did; a
server with the key ignores it whenever a token is sent.

## The three states

| `FLEET_AGENT_IDENTITY_KEY` | `FLEET_AGENT_IDENTITY_ENFORCE` | What a server does |
|---|---|---|
| empty | (must be `false`) | As before tokens: a caller is believed by the name it gives. |
| set | `false` | A token is verified when one is sent, and such an agent is held to its grants. A caller without a token is still served by the name it gives, and is logged (`agent_identity_unverified_call`, at most once in ten minutes per name). |
| set | `true` | A caller without a valid token is refused with `401` and `agent_identity_required`. |

A token that is present and wrong is refused in every state (`401`, `agent_identity_invalid`): it
is never treated as "no token". Enforcement without a key stops the service at startup
(`agent_identity_misconfigured`).

The middle state is what makes a rollout possible: services are deployed one at a time, agents are
reprovisioned after them, and the coordinating agent is not reprovisioned automatically.

## Turning it on

1. Upgrade the orchestrator and the other services (`./upgrade.sh` adds the key and
   `FLEET_AGENT_IDENTITY_ENFORCE=false`).
2. Reprovision **every** agent, the coordinating agent included. Each gets its token.
3. Watch the logs of each server for `agent_identity_unverified_call`. A name that still appears is
   an agent that has not been reprovisioned, or a caller that is not an agent.
4. Set `FLEET_AGENT_IDENTITY_ENFORCE=true` in `.env` and recreate the services.

To go back, set it to `false` and recreate the services. No agent needs reprovisioning for that.

## Which servers

| Server | Name in grants | What the caller's identity decides there |
|---|---|---|
| Orchestrator `/mcp` | `fleet-orchestrator` | Which tools it may call. |
| fleet-memory | `fleet-memory` | Which tools it may call, which projects it may read and write (when the project ACL is on), and whose name a stored memory carries. |
| fleet-telegram | `fleet-telegram` | Which tools it may call, and whose bot sends the message or reaction. |
| Temporal bridge | `fleet-temporal` | Which tools it may call, whether it is the CTO (gate feedback, a forwarded grant approval), and who a human-input request, a `notify_cto` or a memory request is from. |

All four read the token and check grants the same way (`Fleet.Shared.Mcp`). None of them takes the
caller's name from the URL or from a tool's arguments any more: a tool asks who called.

Three tool arguments used to let the model type a name: `memory_store`'s `agent` (the author),
`request_memory_store`'s `agent` (the requester, to whom a revision request is sent) and
`get_chat_info`'s `agent_name` (whose bot to use, which won over the caller). Each is now ignored
when the call is made as an agent, and stands only for a caller that is not one.

The three servers that are not the orchestrator read every agent's grants from the orchestrator's
`GET /internal/agent-mcp-grants`, every 30 seconds, and once more when an agent they have not heard
of calls. `AgentIdentity__OrchestratorUrl` says where (default `http://fleet-orchestrator:3600`).
After ten minutes without a successful read a server no longer believes what it holds, and refuses
verified agents under enforcement (`tool_grants_unavailable`) rather than serve from a list nobody
can vouch for.

### fleet-memory's REST API

`/internal/*` on fleet-memory lists, reads, changes and deletes any memory with no project check.
It is the orchestrator's, for the dashboard's Memory page, and never an agent's. The orchestrator
now sends its service token with every such request. Under enforcement fleet-memory serves these
routes to a service token only: an agent's own token, valid as it is, gets `403` and
`service_identity_required`. Until enforcement they are served as they always were.

### The orchestrator's MCP endpoint

`/mcp` takes no sign-in credential, because agents have none. It is served to:

- an agent with a valid token, for the tools it is granted;
- the operator: the service bearer (`ORCHESTRATOR_AUTH_TOKEN`), a signed-in browser, or a service
  token. An enrolled phone is not an operator here;
- while enforcement is off, anybody, as before.

`GET /internal/agent-mcp-grants` serves every agent's grants on the four servers, for the other
servers to check against. It is Docker-network-only and takes no credential, like
`/internal/agent-project-access`: names of agents and of tools.

## Networks

Identity on the MCP servers is only as good as the absence of a way around them. Two services
take no credential at all, and used to share `fleet-net` with the agents:

| Service | What an agent on its network could do | Now on |
|---|---|---|
| Temporal (`temporal-server`, `temporal-ui`, `temporal-postgresql`) | Signal any gate, cancel or terminate any workflow, without the bridge and its checks | `fleet-temporal-net`, with the orchestrator and the Temporal bridge |
| Qdrant | Read and delete memory vectors without fleet-memory and its project check | `fleet-memory-net` (internal), with fleet-memory |

No agent joins either network: agents are provisioned onto `fleet-net` and whatever networks an
operator adds to them. The host ports (`7233`, `8080`) are unchanged, and loopback by default.

A deployment with its own compose file gets this only by making the same change there. An
existing stack needs its services recreated once (`./upgrade.sh` does) so they join the new
networks; no data moves.

Not closed by this: RabbitMQ is on `fleet-net` because agents use it, with one shared account, so
an agent can still publish to another agent's queue. `fleet-bridge` (port 3300) takes no
credential and prompts the CTO agent by design, for callers outside the fleet. Both are separate
pieces of work.

## Limits

- **Claude and Codex agents only.** A Gemini agent's CLI is not proven to send MCP headers, and an
  agent whose provider does not send them would skip a server that has one. So a Gemini agent gets
  no token, is an unverified caller, and is refused once enforcement is on.
- **An agent whose name cannot be a token's subject gets no token.** A name must be 1 to 128 of
  `A-Z a-z 0-9 _ -`.
- **A token is not revoked one agent at a time.** A deleted agent's token still verifies; it is
  granted nothing, because grants are read from the stored agents. Rotating the key revokes every
  token: prepend the new key (`new,old`), reprovision every agent, then remove the old key.
- **An agent can read its own token** (it is in its MCP configuration). That is its own identity,
  and the point is that it cannot produce another's.
- **The key must never reach an agent.** It cannot be attached as an Env Ref (`env_ref_reserved`),
  by the operator or by anyone, and provisioning does not deliver it even where a stored row names
  it. An agent with the Docker socket, or with the host, is outside this boundary as it is outside
  every other.
- **A grant of the whole server** (`mcp__fleet-orchestrator`) grants every tool of it, now and later.

## An MCP client that is not an agent

Once enforcement is on, a client outside the fleet (a laptop pointed at a fleet server) needs a
credential. Mint a service token on the host and give it to the client as its `Authorization`
header:

```bash
scripts/mint-identity-token.sh service operator
```

It prints the token and nothing else. Whoever holds it is not held to any agent's grants.

## Settings

| `.env` | Service setting | Default | Meaning |
|---|---|---|---|
| `FLEET_AGENT_IDENTITY_KEY` | `AgentIdentity__Key` | generated | base64url, at least 32 bytes. A comma-separated list rotates: the first signs, all verify. |
| `FLEET_AGENT_IDENTITY_ENFORCE` | `AgentIdentity__Enforce` | `false` | `true` refuses a caller without a valid token. Anything but `true` or `false` stops the service. |
| (none) | `AgentIdentity__OrchestratorUrl` | `http://fleet-orchestrator:3600` | Where fleet-memory, fleet-telegram and the bridge read agents' grants. |

All four services read the same key and the same switch. A service with enforcement on and one
without disagree only about callers that have no token, so turn it on for all of them together.

## Tests

`tests/Fleet.Orchestrator.Tests/Identity/`: the token and the rule for who a caller is; the shared
middleware and grant filters against a real MCP server hosted in the test and called by the real
MCP client; what provisioning writes for each provider; the orchestrator's endpoint behind its
production pipeline; the grant cache the other servers use; and a check of the three servers'
sources that none reads the caller from the URL. Each server's own tests cover its routes and its
tools with the caller set as the middleware sets it. Nothing here has run against a deployed fleet
or a provider's own CLI.
